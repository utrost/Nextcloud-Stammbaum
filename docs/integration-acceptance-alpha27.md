## Boundaries still open

The server's public calendar manager cannot prove outward sharing of an owned collection or expose a reliable supported-component set. Browser choices are filtered through authenticated same-origin DAV; unknown audience is labeled **unknown**, never private. Direct API review may accept a collection whose DAV endpoint later refuses the component. Discovery is capped at 50 collections but does not yet page beyond that cap. These remain [#81](https://github.com/utrost/Nextcloud-Stammbaum/issues/81) acceptance gaps.

The Tasks reservation and browser DAV PUT cannot form one transaction. A revoked user can still write the previously issued VTODO during this interval; the local link is invalidated but the external copy needs management in Tasks. Calendar creation has before/after checks but no cross-app transaction. The user-facing reviews disclose independent destination sharing and synchronized copies. Complete all-role, all-source, shared/read-only collection, account recreation, recovery and protocol/log matrix coverage remains in [#86](https://github.com/utrost/Nextcloud-Stammbaum/issues/86). The workflow-specific EN/DE and failure-state matrices in [#83](https://github.com/utrost/Nextcloud-Stammbaum/issues/83) and [#84](https://github.com/utrost/Nextcloud-Stammbaum/issues/84) also remain open. No original parity issue is closed by this integration evidence.

The authenticated route bounds and error behavior are documented in the [integration API contract](integration-api-contract.md). The [Tasks](tasks-iteration.md), [Calendar](calendar-iteration.md) and [Connections](connections-iteration.md) notes describe the supported user workflows and limitations.
