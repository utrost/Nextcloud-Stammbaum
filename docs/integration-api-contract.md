# Same-instance integration contracts (alpha.27)

This records the implemented, authenticated contracts for [#81](https://github.com/utrost/Nextcloud-Stammbaum/issues/81). It is scoped to the optional Tasks, Calendar and Contacts adapters; the full native API/OpenAPI route policy remains [#41](https://github.com/utrost/Nextcloud-Stammbaum/issues/41). Every app route requires a signed-in, enabled Nextcloud account. Mutation routes use Nextcloud CSRF protection; read routes are private and return `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. Nothing here grants Nextcloud administrators implicit tree access.

| Contract | Bound and behavior |
| --- | --- |
| `GET /integrations/tasks/collections`, `/integrations/calendar/collections` | At most 50 current-account collections in total. `items` contains writable choices; `readOnlyItems` contains explicitly marked `read-only` entries that cannot be chosen. `available: false` returns no names. Each item has opaque `uri`, display `name`, `audience` (`shared-with-me` or `unknown`) and `componentCheck: authenticated-dav`. The public calendar manager checks create permission; the signed-in browser checks VTODO/VEVENT support through same-origin DAV before offering a choice or showing a read-only note. `unknown` never means private. Generated Contacts birthday calendars are excluded. |
| `POST /trees/{tree}/tasks/review`, `/calendar/review` | One current authorized source: task `person`, `source`, `event` or `medium`; calendar `person` or `event`. A review binds source, destination, current source and tree revisions, membership generation, dependency digest, reviewed fields and a five-minute expiry. Missing export authority is forbidden; unreadable source/dependency IDs are opaque not-found responses. Living/unknown and management-only content needs an explicit inclusion flag. |
| `POST /trees/{tree}/tasks`, `/calendar` | One acknowledged review and actor-bound 8–80-character request ID. Same request and payload reuse the same random object identity; conflicting reuse fails. At most 20 new operations per account per hour per adapter. Tasks returns one bounded VTODO for same-origin `If-None-Match: *` DAV publication; Calendar creates one VEVENT through the public calendar interface. Both recheck source and destination authority; uncertain external outcomes never masquerade as confirmed links. |
| `POST /trees/{tree}/tasks/{id}/complete` | Verifies a pending VTODO by its deterministic UID through the public calendar search. Lost export authority gives an opaque not-found response; changed source, membership or dependency prevents confirmation. This does not edit a genealogy fact. |
| `GET /trees/{tree}/tasks`, `/calendar` | At most 25 current-account links for one currently readable typed source. Task completion is read from the destination as `open`, `complete` or `unknown`; deleted/unreadable destinations show a changed/unavailable status rather than a linked task, and source-changed links do not expose completion. Calendar distinguishes linked, changed and unavailable. |
| `GET /trees/{tree}/connections`, `POST /connections/{kind}/{id}/refresh` | At most 25 actor-owned receipts per page. Source labels are projected only after current tree, source, dependency and account-incarnation checks. An invalid link stays opaque, including after regrant. Refresh reads the destination under the acting account's ACL and never recreates it. |
| `DELETE /trees/{tree}/connections/{kind}/{id}` and the separate ETag review/removal routes | Local unlink never deletes the destination. A newly app-created, unchanged task or event can be removed only after a fresh review and a conditional DAV `If-Match` delete; pre-existing cards and legacy items without a trustworthy initial ETag are ineligible. |

The server uses only Nextcloud public account, calendar and contacts interfaces and the signed-in browser's same-origin DAV session. It neither stores credentials nor accesses another app's tables. No remote URL is accepted as an adapter destination. Task/calendar receipts contain IDs, hashes, revisions, status and timestamps, not durable copies of task/event bodies. Account-owned connection pages cannot enumerate another user's collection names or records. Published task/calendar data and synchronized devices remain under the destination app's independent permissions.

The public Nextcloud 34 `ICalendar` contract does not expose a reliable supported-component set or prove outward sharing of an owned calendar. Accordingly, UI choices are DAV-filtered, direct API review does not assert component compatibility, and all unproven audiences are marked `unknown`. DAV refuses a VTODO sent to a VEVENT-only collection. A revocation after the server returns a VTODO but before the browser writes it cannot be rolled back across apps; post-write verification suppresses the active Stammbaum link and leaves an opaque cleanup receipt. This boundary is tested with a fictional actual DAV write. Calendar server-side creation also has no cross-app transaction, though it checks before and after its write.

Errors use a stable `error` code and user-facing `message` with HTTP 400/403/404/409/412/422/429 as appropriate. Body text and destination content are absent from safe error responses and logs. Review failure preserves the browser draft; source/destination conflicts require a new review. Task opening falls back to the Tasks list, since a supported stable item deep link has not been verified. Integration details and verified versions are in the [Tasks](tasks-iteration.md), [Calendar](calendar-iteration.md), [Contacts](contacts-iteration.md) and [connection lifecycle](connections-iteration.md) notes.
