# Alpha.26: private integration connections

This iteration implements the account-private connection lifecycle in [#82](https://github.com/utrost/Nextcloud-Stammbaum/issues/82) for the currently supported **person → Tasks, Calendar or Contacts** journeys. It does not add automatic synchronization or make external copies part of genealogy data. Every connection belongs to the acting Nextcloud account, even when several people share the tree. A Nextcloud administrator has no implicit right to another account's links.

## Registry and authority

The three provider-specific link tables form one typed private registry. A schema migration adds an account-incarnation token, source revision/dependency digest, destination ETag slot and status fields. Contacts links retain their card identity and content hash; task and event receipts retain a random object name, UID derived from that name, request ID and reviewed payload hash. No credential or DAV body is persisted. The new account token is random and is deleted with all private links on account deletion/recreation. Pre-migration links are assigned an account token only on an authorized read with their original membership still current; old Contacts links take that moment as the first available source-revision baseline. Legacy links without an initial ETag remain readable but cannot be removed externally from Stammbaum.

**Connections** lists at most 25 links per page, filtering by account and tree in SQL before pagination. A link's source label and **Open source** action appear only if current tree membership, relevant export grant, account incarnation, membership generation and person visibility all still allow them. Lost tree access, hidden/deleted sources and invalidated authority leave only an opaque private cleanup row. Refresh performs current read-only destination checks; it never republishes a missing object or overwrites an edited one. Source revision changes display **Source changed** and require a new reviewed copy. A restored source or regranted membership never reactivates an old operation. Refresh and unlink do not change tree revisions or genealogy history.

Pending operations become **Outcome uncertain** after five minutes. Idempotency receipts and deterministic UIDs prevent a repeated confirmation from creating another task or event while the original reviewed operation is valid. Local unlink retains a tombstone for 30 days and leaves the external item untouched; uncertain receipts are retained for 90 days before pruning. A daily Nextcloud job prunes only local private receipts and does not access DAV or originals. Account deletion removes its receipts immediately. The post-recovery `stammbaum:invalidate-authority` command advances membership generations and invalidates unfinished connection operations before further writes.

## Reviewed external removal

For a newly created Calendar event or Tasks item, the signed-in browser attempts to capture the first DAV ETag within 60 seconds of creation. If that capture fails or arrives late, in-app external removal stays unavailable; the user can still unlink locally or manage the item in Calendar/Tasks. A pre-existing Contacts card is never eligible for deletion from Stammbaum. An older app-created item without an initial ETag is also ineligible.

The separate **Review external removal** action checks current source and destination access, creation ownership and the stored ETag. Explicit refresh and removal review read the current DAV ETag in the acting browser; a mismatch durably marks the destination changed. The browser shows a deletion warning and requires a separate acknowledgement. Immediately before deletion it obtains a fresh server review and checks the ETag again. It sends a same-origin DAV `DELETE` with `If-Match`; a changed item is refused. The server closes the local receipt only after rechecking source authority and verifying the UID is absent. A lost response or failed verification remains uncertain and can be refreshed or unlinked without making a second external item. A destination move is treated as a changed destination, not searched by name or silently deleted elsewhere.

This is a foreground operation by the acting account. There is no cross-app transaction: a revocation between the final server check and DAV request cannot recall a copy or deletion already accepted by the other app. The UI reports independent ownership and asks the user to inspect the destination when the outcome is uncertain. No background DAV write, administrator impersonation, shared registry or bulk external cleanup is introduced.

## Verification and remaining integration scope

The isolated Nextcloud 34 fixture exercises owner isolation, source edit/deletion, revoke/regrant, opaque cleanup, uncertain receipts, tombstone pruning, keyboard and 1440/390/320-pixel layouts, unchanged genealogy revisions, unchanged-item deletion and stale-ETag refusal. Existing Tasks/Calendar/Contacts tests cover reviewed creation, repeat confirmation, missing destinations and absent optional apps. The full browser suite, Alice smoke, CI and package evidence are recorded with the corresponding delivery; these statements do not assert unexecuted checks.

The current adapters still start from a person. Shared-event and media entry points, richer task status/completion, reviewed external updates, collection audience classification and additional failure injection remain in [#81](https://github.com/utrost/Nextcloud-Stammbaum/issues/81), [#83](https://github.com/utrost/Nextcloud-Stammbaum/issues/83), [#84](https://github.com/utrost/Nextcloud-Stammbaum/issues/84) and [#86](https://github.com/utrost/Nextcloud-Stammbaum/issues/86). Older links cannot gain a trustworthy creation ETag retroactively. Contacts remain linked read-only and can be unlinked locally; the confidential-copy action continues to require its own explicit review.
